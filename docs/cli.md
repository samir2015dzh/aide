# The `aide` CLI, for agents

Agents that run on a computer (Claude Code, Codex, Cursor, your own) use
Aide through the `aide` command line. Install and sign in:

```bash
curl -fsSL https://github.com/samir2015dzh/aide/releases/latest/download/install.sh | sh -s -- --cli
aide auth login relay.example.com --account me --name "Codex on MacBook"   # asks for the password
```

`aide auth login` logs this agent in to the owner's server with their account and password ([docs/accounts.md](accounts.md)): the server signs it in at once, with nothing to approve or compare. The server is the argument, else `$AIDE_SERVER`; the account is `--account`, else `$AIDE_ACCOUNT`, else asked for; the password is asked for, or read with `--password-stdin`, or taken from `$AIDE_PASSWORD`. The agent may use every machine, project and coding agent, and see its own sessions, until the owner revokes it or changes the password; the owner can narrow or widen that in the app.

`aide auth status` checks the login step by step (the local identity, the grant, the relay connection, whether the grant is current) and gives the next command when something is wrong. If you were revoked or signed out by a new password, run `aide auth login` again: it logs in afresh as a new agent. To switch owners, run `aide auth logout` first.

`aide agent login antigravity` signs in to the official Antigravity ACP server **on the computer running this command**, separately from the Aide login. It prints the Google sign-in link and leaves credentials with the official server. `--method` selects another advertised authentication method. See [installation and authentication](antigravity.md).

Commands are "noun + action": `auth`, `project`, `session` and `message`, each with its actions (`aide <noun> --help`). The agent calling the CLI is the **client**; the agent doing the work on the machine is the **coding agent** (`--agent claude`). Over MCP, the same commands are tools (`project_list`, `session_start`, …; [docs/mcp-gateway.md](mcp-gateway.md) §7).

```bash
aide project list                # where you can work: machine/project, the owner's notes, branch, platform, usable coding agents, whether a session can start now
aide session start --project vps-1/demo --agent claude --wait --prompt "Fix the bug on the login page"   # demo alone is enough if only one machine has it
aide session start --project demo --title "Login page bug" --prompt "..."   # a title for the app and session list; default: the prompt's first line
aide message send --to s_xxx --wait --message "Add one more test"   # the one way to tell a session anything; while it runs, the message joins your turn
aide message send --to s_xxx --wait -f screenshot.png -f spec.pdf --message "Change it to match these"   # attach files
aide session answer s_xxx --wait --choose 2   # answer the agent's question (also --text, --decline, or just write to the session)
aide session wait s_xxx --timeout 5m   # wait again for a session started without --wait, or after a wait_timeout; sends nothing
aide session diff s_xxx
aide session list                # your sessions (--archived for archived ones)
aide session list --native       # also the DeepSeek Harness sessions Aide did not start, read-only (dsh_…: session get / events)
aide session interrupt s_xxx     # stop the running turn; the session stays, and a later message continues it
aide session archive s_xxx       # when done: read-only, frees the worktree (the branch keeps the changes); unarchive restores it
aide session events s_xxx --after 812   # events page by page: the latest 50 by default; --after newer, --before older
aide machine exec vps-1 --workdir '~/app' -- git pull --ff-only   # a one-shot shell command on a machine, if the owner allowed this agent to run commands (docs/machine-ops.md)
aide work --days 7                # what the coding agents did over the last 7 days (default: today): sessions, turns, tokens, time, by agent and by who sent the work
aide message list --wait         # your inbox: news of your sessions, messages from the owner's other agents
aide --as "Tech Demos" session start --project web --prompt "…"   # several bots share this agent? each passes its own name: its news and replies come back to it alone
aide --as "Tech Demos" message wake   # started by a webhook (a Grok Bot routine)? a one-time link for your owner, who pastes its URL and key: then Aide wakes you when messages arrive
aide message ack msg_xxx         # handled: it leaves the inbox
aide message send --to "Grok Bot" --message "PR #143 is ready"   # to another of the owner's agents (message contacts lists them)
```

**Messages to a session.** `message send --to <session>` goes straight to its machine when it's online. If you asked for the turn running now, it joins it (Claude Code and Codex take it at the next tool boundary) and answers its question; otherwise it starts a turn of its own, or waits for one, so one agent's words never go into another's turn. Any agent whose grant covers the session and that may see it can write to it; only the agent that started it can interrupt or archive it (and Her, whose grant covers every session she may see: [her-team.md](her-team.md) §6.1). While the machine is offline the message waits for it (files need it online). `session send` still works for now, as an alias.

**DeepSeek Harness's own sessions (read-only).** `session list --native` also lists, from each machine, the DeepSeek Harness (DSH) sessions Aide did not start: the owner's in DSH Desktop, another tool's, as DSH keeps them on disk. Each has an id `dsh_<machine>_<DSH's id>` (never an `s_` id), its title, state (`running`, `idle`, `ended`, or `unknown` where the machine can't tell), folder and last activity. `session get dsh_…` and `session events dsh_…` read one; nothing else does: sending it a message, answering, interrupting, archiving or taking it over fails with `invalid_state` (exit code 2), since it is DSH's, not an Aide session; continue it in DSH, or start a session of your own. Which ones an agent sees follows its grant as for sessions it did not start: a grant that sees all sessions sees the DSH sessions working in the projects it covers (in any folder with all projects), on the machines it covers; a grant that sees only its own sessions (the default) sees none, as no DSH session is an agent's own. Sessions Aide started with DSH are listed as sessions, not here. A machine whose Aide predates this lists none.

**Your inbox.** When a turn of a session you started ends, asks a question or fails while you aren't waiting on it (no `--wait` running), its news comes to your inbox as a message, sealed end to end, and waits there, even while you're offline, until you acknowledge it (30 days at most). Every command's JSON says `inbox.waiting` while messages wait. `message status` tells what became of a message, `message contacts` lists the owner's agents and machines. See [docs/agent-messages.md](agent-messages.md).

**Claude Code and Codex on your computer.** `aide message hook claude --install` (or `codex`) adds Aide's hooks to the agent's user settings. Each conversation then gets the messages addressed to it, such as news of the sessions it started and replies to what it wrote: at the start of its turns and when a turn would end, and in Claude Code also between tool calls and while idle (a new turn). Messages addressed to no conversation stay in the inbox; the hooks only say how many wait. In Claude Code the conversation's commands know its key (`AIDE_AS`); from Codex, add `--as <key>` to the commands.

**Sessions never end on their own.** However long one has been idle, another message continues the same coding agent session.

**Questions mid-turn.** Claude Code (AskUserQuestion), Codex and ACP agents with form questions can ask in the middle of a turn. The session goes to `waiting_input`; `--wait` returns at once with exit code 8 and prints the question and options. Answer with `session answer` (`--choose` a label or number, `--text`, or `--decline`), with `session send` (the message is the answer), or on the session page in the app. Unanswered, a question expires after 30 minutes by default and the agent is told to use its own judgment and state its assumptions; `session start --question-timeout 0` means nobody will answer in this session. Answers to secret questions go only to the agent and aren't recorded in events.

**Projects** are added by the owner in the app, or on the machine with `aided project`; a machine's projects, workspace roots, agent defaults and custom agents export as one YAML file and apply again with `aided config export` / `aided config apply -f <file> [--dry-run]`, the owner's command on the machine, not an agent's ([machine-ops.md](machine-ops.md) §6). Any directory can be one, with a worktree switch: **separate worktree** (the default for a git repository root: each session on its own branch `aide/<session>` from `--base`, a snapshot every turn, changes shown by `session diff`; ignored local files named in the repository's `.worktreeinclude` are copied in) or **in place** (the only option outside git: the agent reads and writes the directory directly, as if you ran it there yourself; no branch, no commits, no diff, and concurrent sessions coordinate among themselves).

**Ports for dev servers.** Each session's coding agent gets a block of ports no other session on its machine has, so dev servers in parallel sessions don't collide: `AIDE_PORT_BASE` is its first port and `AIDE_PORT_COUNT` how many there are (10: `AIDE_PORT_BASE` to `AIDE_PORT_BASE+9`). Blocks are taken from 20000-26999, above the usual development ports (3000, 5173, 8080…) and below every system's ephemeral ports (Linux 32768 and up, macOS and Windows 49152 and up). A session keeps its block for as long as it is not archived: across turns, a restart of aided and a crashed agent's next start; archiving frees it for the next session that needs one, and an unarchived session gets a block afresh. Beside them are `AIDE_SESSION` (the session id, for a name or subdomain such as `$AIDE_SESSION.localhost`), `AIDE_WORKTREE` (the directory the session works in: its worktree, or the project directory in place) and a `TMPDIR` of the session's own; the branch is `git branch --show-current` there. Agents should start dev servers on these ports rather than their defaults, e.g. `npm run dev -- --port $AIDE_PORT_BASE`, `python -m http.server $((AIDE_PORT_BASE+1))`, or `PORT=$AIDE_PORT_BASE` for servers that read `PORT`; a project's scripts can use `${AIDE_PORT_BASE:-3000}` to keep their default outside Aide. In-place sessions get a block too, but they share one directory: what is written there (a `.env`, a lock file) is shared as well. Machines whose Aide predates this set none of these but `AIDE_SESSION` and `TMPDIR`.

**GitHub repositories.** `session start --repo owner/repo` (or its URL; `--branch` to start from another than the default branch, `--machine` when several machines are online) works in a GitHub repository nobody added as a project. The machine checks at once that its own git login reaches it (gh, a credential helper or an ssh key; Aide keeps no credentials), and fails with why if not: it never falls back to a project. It clones the repository into its data folder (`repos/github.com/<owner>/<repo>`), or fetches the clone an earlier session made, keeps the clone as the worktree project `github.<owner>.<repo>`, and the session works there as in any worktree project; `session get` shows `repo` and `repo_branch`. It takes a grant for every project (or for that project). Nothing is ever pushed by itself: `session push <id>` pushes the session's branch to the repository's remote origin with the machine's login (any worktree session's, to its project's origin) and gives the page to open a pull request; the owner can push from the app too.

**Files.** `-f/--file` can be repeated, up to 20 files and 32 MiB per message. They're saved in the session's attachments directory on the machine (outside the worktree, so never in the diff), and the message lists their paths; PNG, JPEG, GIF and WebP images up to 3.5 MiB also go to the agent as images.

**Waiting.** `session start`, `send` and `answer` return once the message is delivered (stderr suggests `aide session get <id>`; after the turn, the session's `result` is the agent's full reply). With `--wait` they wait for the turn to end and the exit code says how it went; from a tool with a time limit, add a shorter `--timeout` (exit code 6; the turn keeps going, follow up with `get`, or wait again with `aide session wait <id>`). `session wait` sends nothing and changes nothing: on a session at work it waits for the turn to end, exactly as `--wait` would; on one that isn't, it returns at once with the exit code of its last turn (0, 5 or 7; 8 with the question when it waits for an answer). No wait ever answers a question: it ends as the agent asks. The session ID is always the first line on stderr, so it's known even if the process is killed midway. The message comes from `--prompt` / `--message` or a file (`--prompt-file`, `--message-file`; `-` for stdin); stdin is never read unless asked for.

**One connection.** The first command connects to the relay by itself and starts this agent's **link**: a background process, one per `AIDE_HOME`, that keeps the connection to the relay and the tunnels to your machines. The commands and hooks after it go through the link, over a local endpoint only your user can open, so they skip the connection and its handshakes (two round trips at least, more to a relay over HTTPS) and the relay sees one connection from this computer rather than one per command. The link only carries calls; each command still checks its grant and lists the machines itself. It ends after 10 minutes without a command, when the agent is revoked or its login is gone. Nothing depends on it: a command whose link does not answer within 3 s, or does not carry its first calls within 5 s, connects by itself as before. `AIDE_LINK=off` makes every command do so.

**On the machine's own computer.** When the machine you work on runs on this same computer (Claude Code on the Mac that also runs Aide), the CLI reaches it directly, not through the relay: its calls never leave the computer. It also works while the relay cannot be reached: a command then goes on with the machines as last listed, this computer's own online and the others not (a warning on stderr says so); your inbox and messages to other agents wait for the relay. Your grant counts as ever. `AIDE_LOCAL=off` sends everything through the relay.

**Output.** Text for people by default; with `-o json` (or `AIDE_OUTPUT=json`) stdout is one JSON document with the same outer shape for every command: `ok`, `exit_code`, `error` (`{kind, message, hint, retryable}` on failure, null on success), and data under named keys (`session`, `sessions`, `projects`, `events`). An offline machine isn't an error: lists come back with it under `offline`; a command fails with exit code 4 only when the machine it needs is offline. See [docs/cli-output.md](cli-output.md).

**Exit codes.** 0 success; 1 internal error; 2 bad arguments, not found, or not allowed now (like sending to an archived session); 3 not logged in, revoked or not authorized; 4 relay or the needed machine offline or unreachable (retryable); 5 session failed; 6 timeout; 7 transient failure (rate limit, network, server error, agent crashed or stuck: send again); 8 the agent is waiting for an answer. A session's latest failure is in `session.last_failure` (`kind`, whether it's retryable, a `hint`); a session that crashed, got stuck or failed to start is `crashed`, and the next message continues with its context.
